# AirPlay Clock Source Investigation

## 1. Purpose

This report identifies the clock that the current CarPlay/AirPlay implementation
actually uses for media time synchronization. It distinguishes three concepts
that are easy to conflate:

1. the AirPlay timing master;
2. the local hardware counter used to follow or generate that timing domain;
3. the software mapping maintained by `AirTunesClock`.

The conclusions below come from the linked image, archive members and available
FreeRTOS platform source. They are not based only on API names.

## 2. Executive conclusion

For the iPhone-to-box AirPlay session, the iPhone is the timing master. Its UDP
timing response supplies the remote `T2` and `T3` timestamps. The Apple hardware
timer behind that clock is internal to the iPhone and cannot be identified from
this firmware.

The box follows that remote clock using this local time base:

```text
Cortex-M SysTick hardware
        -> FreeRTOS xTickCount (1000 Hz)
        -> clock_gettime(CLOCK_MONOTONIC)
        -> GetTickCount()
        -> UpTicks()
        -> AirTunesClock software offset/rate correction
```

For the box-to-head-unit AirPlay session, the box is the timing server. Its
timing response is generated by `AirPlayTimer_SetTimeRTCPData()` using
`gettimeofday()`. In this image the elapsed-time component of `gettimeofday()`
is also derived from FreeRTOS `xTickCount`, and therefore from Cortex-M SysTick.

The AirPlay implementation does **not** use the 2 MHz system GTimer, RTC, or a
Wi-Fi MAC hardware receive timestamp as its local media clock source.

## 3. Inbound session: iPhone is the clock master

The receiver sends a 32-byte timing request (`0xD2`) and receives a 32-byte
timing response (`0xD3`). The timestamps have the normal four-point timing
meaning:

```text
T1: box sends request
T2: iPhone receives request
T3: iPhone sends response
T4: box receives response
```

The receiver calculates:

```text
offset = ((T2 - T1) + (T3 - T4)) / 2
RTT    =  (T4 - T1) - (T3 - T2)
```

Therefore, the authoritative clock in this direction is the iPhone clock used
to produce `T2` and `T3`. `AirTunesClock_Adjust()` applies the measured offset
and long-term rate correction to the box's local counter. It does not tune a
PLL, RTC or hardware timer.

The implementation filters timing samples by RTT and smooths the correction so
that network and scheduler delay do not immediately move the media timeline.

## 4. Local clock call chain

Disassembly of `TickUtils.o` shows that `UpTicks()` directly calls
`GetTickCount()` and then clears the upper 32 bits of its 64-bit return value:

```asm
UpTicks:
    bl      GetTickCount
    movs    r1, #0
```

The linked `GetTickCount()` implementation calls:

```c
clock_gettime(CLOCK_MONOTONIC, &time);
```

It converts the result to milliseconds. The local POSIX implementation of
`CLOCK_MONOTONIC` calls `vTaskSetTimeOutState()` and constructs the time from
FreeRTOS tick count plus its overflow count.

The configured tick rate is:

```c
#define configTICK_RATE_HZ 1000
```

FreeRTOS configures the Cortex-M SysTick registers at:

```text
0xE000E010  SysTick CTRL
0xE000E014  SysTick LOAD
0xE000E018  SysTick CURRENT
```

with a reload derived from:

```c
configSYSTICK_CLOCK_HZ / configTICK_RATE_HZ
```

`configSYSTICK_CLOCK_HZ` defaults to `configCPU_CLOCK_HZ`, whose value is
`SystemCoreClock` in this project. Consequently the FreeRTOS setup code adjusts
the SysTick reload to retain a 1 ms tick at the configured CPU clock.

The result is a nominal 1 ms local AirPlay timing resolution. `UpTicks()` also
zero-extends a 32-bit millisecond value, so its raw value wraps after
approximately 49.7 days. The synchronization code works with values near the
current time, but this wrap behavior should be remembered for unusually long
continuous sessions.

## 5. Receive timestamp is not a hardware packet timestamp

`_TimingInitialize()` calls:

```c
SocketSetPacketTimestamps(socket, 1);
```

However, disassembly of this platform's `NetUtils.o` shows that the function is
a stub:

```asm
SocketSetPacketTimestamps:
    movs    r0, #0
    bx      lr
```

It returns success without configuring lwIP, the WLAN MAC, or another hardware
timestamp unit.

`SocketRecvFrom()` performs this sequence:

```text
lwip_recvmsg()
    -> UpTicks()
    -> store the result as packet receive ticks
```

Thus `T4` is sampled in software after `lwip_recvmsg()` returns. It includes an
unknown amount of WLAN-driver, lwIP mailbox and task-scheduling delay, and it is
quantized to the 1 ms FreeRTOS time base. It is not the exact time at which the
first packet bit arrived at the Wi-Fi MAC.

The RTT filter and repeated timing exchanges help tolerate this limitation, but
they do not turn it into a hardware receive timestamp.

## 6. Outbound session: box is the clock master

In the box-to-head-unit session, `AirPlayTimer.o` implements the timing server.
`AirPlayTimer_SetTimeRTCPData()` calls `gettimeofday()` twice to create the
receive (`T2`) and transmit (`T3`) timestamps in the `0xD3` response.

The linked `gettimeofday()` implementation uses the FreeRTOS real-time clock
layer. Its epoch base comes from the software/SNTP time state, while elapsed
time is calculated from `xTaskGetTickCount()`. Therefore the oscillator/rate
source underneath this timing server is again Cortex-M SysTick.

`AirPlayScreen_SendScreenNormalFrame()` also obtains `UpTicks()` and converts
it with `UpTicksToNTP()` when stamping outgoing screen frames. This is the same
FreeRTOS millisecond time base, expressed as NTP fixed-point time.

## 7. What AirTunesClock actually does

`AirTunesClock_Create()` initializes a nominal frequency of 1000 ticks per
second. Its worker calls `_AirTunesClock_Tick()` approximately every 10 ms, but
queries extrapolate from the latest state using the current `UpTicks()` value.

Conceptually it maintains:

```text
synchronized media time
    = local UpTicks * corrected rate + synchronized offset
```

Large initial errors can step the virtual clock. Smaller errors are gradually
slewed by changing the software rate/offset state. No hardware clock register
is modified by `AirTunesClock_Adjust()`.

This synchronized mapping is then used to:

- convert incoming screen-frame NTP timestamps to local presentation ticks;
- align the audio RTP timeline with local playback time;
- estimate clock-rate drift and protect the audio jitter buffer;
- decide whether media data is early, on time or late.

## 8. Tickless behavior

With `configUSE_TICKLESS_IDLE=1`, FreeRTOS may stop or extend SysTick while the
CPU is idle and advance `xTickCount` by the suppressed interval after wake-up.
The AirPlay API still observes a logical 1 ms monotonic tick count.

This does not change the AirPlay clock source to GTimer or RTC. Its accuracy
depends on the Cortex-M SysTick tickless implementation and correct
`SystemCoreClock`/reload configuration.

### 8.1 Compensation is calculated in CPU cycles, not milliseconds

The RTL8195B FreeRTOS port clocks SysTick from the CPU core clock:

```c
configSYSTICK_CLOCK_HZ = configCPU_CLOCK_HZ = SystemCoreClock;
```

At a 360 MHz CPU clock and a 1000 Hz FreeRTOS tick rate:

```text
ulTimerCountsForOneTick = 360,000 cycles
one SysTick count       = 1 / 360 MHz = approximately 2.78 ns
one FreeRTOS tick       = 360,000 counts = 1 ms
```

When entering tickless idle, the implementation first reads the remaining
count in the current SysTick period. It then programs:

```text
reload = current_remaining_cycles
       + cycles_per_tick * (expected_idle_ticks - 1)
       - stopped_timer_compensation
```

`portMISSED_COUNTS_FACTOR` is 45 in this port. Because SysTick and the CPU use
the same clock, this corresponds to:

```text
45 / 360 MHz = 0.125 us
```

This fixed cycle count compensates for instructions executed while SysTick is
stopped and restarted. It is not a 1 ms correction.

If an unrelated interrupt wakes the CPU early, the port reads
`SysTick->CURRENT` and calculates the number of hardware counter decrements
that elapsed. The result is separated into:

```text
complete tick periods -> vTaskStepTick()
fractional tick cycles -> next SysTick LOAD value
```

Consequently, an incomplete millisecond is not discarded. Its sub-ms phase is
preserved by arranging for the next normal SysTick interrupt to occur after the
correct remaining number of CPU cycles.

If the extended SysTick itself expires, the implementation advances
`xTickCount` by one less than the requested interval and lets the pending
SysTick interrupt account for the final tick. It also restores the remaining
phase before returning to the normal 1 ms reload value.

### 8.2 What remains limited to 1 ms

The tickless accounting is cycle based, but `UpTicks()` exposes only the
integer FreeRTOS millisecond count. It does not combine `xTickCount` with the
current SysTick counter value.

Therefore:

- tickless does not introduce a new error of up to 1 ms on every sleep;
- the fractional phase remains in hardware and is carried into the next tick;
- an arbitrary `UpTicks()` sample is still quantized to 1 ms;
- that 1 ms quantization exists with tickless enabled or disabled.

The small residual tickless error is the difference between the fixed 45-cycle
compensation and the true stop/restart instruction cost. Its expected scale is
sub-microsecond per transition, not millisecond scale.

### 8.3 SysTick range at 360 MHz

SysTick has a 24-bit reload register. At 360 MHz the maximum single suppressed
interval is approximately:

```text
0xFFFFFF / 360 MHz = 46.6 ms
```

FreeRTOS caps `xExpectedIdleTime` to this range. Long idle periods therefore
consist of repeated bounded tickless intervals rather than one unbounded sleep.

### 8.4 CPU-clock dependency

SysTick is directly clocked by the CPU clock. FreeRTOS computes its reload and
tickless constants when the scheduler starts. This project applies the system
PLL change at the beginning of `main()`, updates `SystemCoreClock`, and starts
the scheduler later. That ordering allows the FreeRTOS setup to calculate the
correct values for the selected CPU frequency.

Changing the CPU clock after the scheduler starts without reconfiguring SysTick
and the tickless constants would change the duration represented by every
FreeRTOS tick. The current boot-time-only clock change avoids this condition.

The remaining important assumption is that the actual PLL output is close to
the frequency assigned to `SystemCoreClock`. `SystemCoreClock` is a software
value, not a frequency measurement. A significant mismatch would produce a
proportional error in SysTick and hence in the local AirPlay clock. Normal
crystal ppm error is expected to be tracked by the periodic AirPlay timing
adjustment; a gross PLL-configuration error is a different case and should be
excluded by measurement.

## 9. System GTimer distinction

The RTL8195B platform also provides a free-running system GTimer:

```text
base address: 0x40002000
configured source: 2 MHz
API: hal_read_curtime_us()
```

That counter is used by local diagnostics and profiling because it provides
microsecond-scale measurement. The inspected AirPlay clock path does not call
`hal_read_curtime_us()` and therefore does not use this timer for media clock
synchronization.

## 11. Practical assessment

For the current configuration, tickless compensation is not a material AirPlay
timing risk. The implementation preserves fractional SysTick phase in CPU-cycle
units, the system does not switch to a clock-gated deep-sleep counter, and
AirPlay periodically corrects its software clock against the timing master.

The practical timing limitations are instead:

1. the `UpTicks()` interface exposes only 1 ms resolution;
2. timing response receive time is sampled in software after `lwip_recvmsg()`;
3. the configured `SystemCoreClock` must represent the real PLL output closely.

Of these, only a large discrepancy between actual PLL frequency and
`SystemCoreClock` would cause a persistent proportional clock-rate error. The
first two affect synchronization measurement precision and jitter, but the RTT
filter and repeated clock adjustment are designed to tolerate them.
